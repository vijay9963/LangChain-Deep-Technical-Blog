Introduction to LangChain

What is LangChain?

LangChain is an open-source Python (and JavaScript) framework designed to simplify the development of applications powered by Large Language Models (LLMs). Created by Harrison Chase in October 2022, it quickly became the go-to orchestration layer for anyone building with GPT, Claude, Llama, or any other foundation model.

At its core, LangChain is a composition framework: it lets you chain together LLM calls, external tools, memory systems, and data sources into coherent, stateful pipelines. Rather than writing raw API calls and stitching logic yourself, LangChain provides reusable primitives — prompts, chains, agents, retrievers, memory — that snap together like LEGO blocks.

Mental Model: Think of LangChain as the plumbing layer between your application and LLMs. Without it, you're hand-wiring every pipe. With it, you plug standardised connectors together and focus on what your application should do, not how it calls an API.

Why is it Important in the Modern LLM Ecosystem?

LLMs in isolation are powerful but limited. A raw GPT-4 call can answer a question, but it cannot remember the last conversation, look up live data, run code, or make decisions across multiple steps. LangChain solves this by providing the scaffolding to build agentic, context-aware applications.

The framework exploded in popularity (100k+ GitHub stars within months) because it abstracts the hardest parts: prompt management, chain orchestration, memory persistence, tool integration, and retrieval-augmented generation (RAG) — all while being model-agnostic.

Problems LangChain Solves

🎯
Orchestration
Coordinate multiple LLM calls, tools, and data sources in a single pipeline with clean error handling and retry logic.
⛓️
Chaining
Compose complex multi-step reasoning where each step's output feeds the next — like a deterministic workflow over LLM intelligence.
🧰
Tool Integration
Let models call web search, calculators, databases, APIs, and custom functions — moving beyond static Q&A.
🧠
Memory
Persist conversation history and user state across turns — building chatbots that actually remember what was said.
📚
Retrieval (RAG)
Inject relevant private documents into LLM context at query time using vector stores and semantic search.
🔌
Model Agnosticism
Swap OpenAI for Anthropic, HuggingFace, or a local Ollama model with a single line change — same chain code throughout.

Core Components of LangChain

1. LLMs & Chat Models langchain_openai

The LLM abstraction is LangChain's foundational primitive. It wraps any language model — GPT-4o, Claude 3, Llama 3, Mistral — behind a consistent interface. There are two flavours:

LLMs take a plain string and return a string. ChatModels take a list of HumanMessage, AIMessage, SystemMessage objects and return a ChatMessage. ChatModels are the modern standard — they map exactly to the conversation-turn model that OpenAI, Anthropic, and others expose.

python · llm_basics.py 
# Install: pip install langchain langchain-openai
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, SystemMessage
import os

# Initialise the model (uses OPENAI_API_KEY env var automatically)
llm = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0.7,     # creativity dial: 0 = deterministic, 1 = creative
    max_tokens=512
)

# Simple invocation with a message list
messages = [
    SystemMessage(content="You are a senior Python engineer. Be concise and precise."),
    HumanMessage(content="Explain Python's GIL in two sentences.")
]

response = llm.invoke(messages)
print(response.content)
# → "The GIL is a mutex that allows only one thread to execute Python bytecode ..."

# Streaming output token by token
for chunk in llm.stream(messages):
    print(chunk.content, end="", flush=True)

2. Prompts & Prompt Templates langchain_core

Prompt Templates are parameterised prompt factories. Instead of f-strings scattered across your codebase, you define a template once and inject variables at call time. This enables prompt versioning, testing, and reuse.

ChatPromptTemplate is the modern way — it creates a list of typed messages from a template. The .from_messages() factory accepts ("system", ...), ("human", ...), and ("ai", ...) tuples.

python · prompt_templates.py 
from langchain_core.prompts import ChatPromptTemplate, PromptTemplate

# ── ChatPromptTemplate (recommended for chat models) ──
chat_prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a {role} expert. Answer in {language}."),
    ("human", "{question}")
])

# Format the prompt — produces a list of BaseMessages
messages = chat_prompt.format_messages(
    role="machine learning",
    language="English",
    question="What is gradient descent?"
)

# ── PromptTemplate (for simple string LLMs) ──
simple_prompt = PromptTemplate(
    input_variables=["product", "tone"],
    template="Write a {tone} tagline for: {product}"
)
print(simple_prompt.format(product="AI tutor app", tone="inspirational"))
# → "Write an inspirational tagline for: AI tutor app"

# ── Partial Templates (pre-fill some vars) ──
partial = simple_prompt.partial(tone="humorous")
print(partial.format(product="coffee machine"))
# → "Write a humorous tagline for: coffee machine"

3. Chains — LCEL LangChain Expression Language

A Chain links components together using the pipe operator |. LangChain Expression Language (LCEL) is the modern way to compose chains declaratively. Every LCEL chain is a Runnable — it supports .invoke(), .stream(), .batch(), and .ainvoke() out of the box.

python · chains_lcel.py 
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

llm = ChatOpenAI(model="gpt-4o-mini")

# ── Simple Chain: prompt | llm | parser ──
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a code review assistant."),
    ("human", "Review this Python snippet:\n\n{code}")
])

chain = prompt | llm | StrOutputParser()

review = chain.invoke({"code": "def add(a,b): return a+b"})
print(review)

# ── Sequential Chain: translate then summarise ──
translate_prompt = ChatPromptTemplate.from_messages([
    ("human", "Translate to French: {text}")
])
summarise_prompt = ChatPromptTemplate.from_messages([
    ("human", "Summarise in 1 sentence: {translated}")
])

from langchain_core.runnables import RunnablePassthrough

full_chain = (
    translate_prompt | llm | StrOutputParser()
    | (lambda x: {"translated": x})
    | summarise_prompt | llm | StrOutputParser()
)

result = full_chain.invoke({"text": "LangChain makes LLM apps easy."})
print(result)

# ── Parallel Chain: run two branches simultaneously ──
from langchain_core.runnables import RunnableParallel

parallel = RunnableParallel({
    "pros": (ChatPromptTemplate.from_messages([("human", "List 3 pros of {topic}")]) | llm | StrOutputParser()),
    "cons": (ChatPromptTemplate.from_messages([("human", "List 3 cons of {topic}")]) | llm | StrOutputParser()),
})

out = parallel.invoke({"topic": "microservices"})
print(out["pros"])
print(out["cons"])

4. Memory langchain_core

LLMs are stateless by default — each API call is independent. Memory gives chains persistence. LangChain offers several strategies: storing the full history (ConversationBufferMemory), a windowed slice (ConversationBufferWindowMemory), a compressed summary (ConversationSummaryMemory), or a token-limited hybrid.

python · memory_example.py 
from langchain_openai import ChatOpenAI
from langchain_core.chat_history import BaseChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_community.chat_message_histories import ChatMessageHistory
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

# In-memory store keyed by session_id
store = {}

def get_session_history(session_id: str) -> BaseChatMessageHistory:
    if session_id not in store:
        store[session_id] = ChatMessageHistory()
    return store[session_id]

# Prompt includes a placeholder for history injection
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a friendly assistant named Aria."),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{input}")
])

llm = ChatOpenAI(model="gpt-4o-mini")
chain = prompt | llm

# Wrap with history management
chat_chain = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="input",
    history_messages_key="chat_history"
)

config = {"configurable": {"session_id": "user_42"}}

resp1 = chat_chain.invoke({"input": "Hi! My name is Ravi."}, config=config)
print(resp1.content)   # "Hello Ravi! How can I help you today?"

resp2 = chat_chain.invoke({"input": "What is my name?"}, config=config)
print(resp2.content)   # "Your name is Ravi, as you mentioned earlier!"

5. Agents ReAct · Tool-Calling

Agents are LangChain's most powerful abstraction. Instead of a pre-defined chain, an agent lets the LLM decide at runtime which tools to call, in what order, and when to return a final answer. This implements the ReAct (Reasoning + Acting) pattern.

Modern LangChain uses tool-calling agents, which rely on the model's native function/tool-calling capability (OpenAI, Anthropic, Gemini all support this) rather than prompt-based parsing. The agent receives a list of tool schemas, picks one, gets the result, then iterates until it has a final answer.

python · agent_example.py 
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langchain.agents import create_tool_calling_agent, AgentExecutor
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

# ── Define tools with @tool decorator ──
@tool
def calculator(expression: str) -> str:
    """Evaluate a mathematical expression. Input: '2 ** 10 + 5'"""
    try:
        return str(eval(expression, {"__builtins__": {}}, {}))
    except Exception as e:
        return f"Error: {e}"

@tool
def word_count(text: str) -> str:
    """Count the number of words in a text string."""
    return f"{len(text.split())} words"

tools = [calculator, word_count]

# ── Create agent prompt ──
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant with access to tools."),
    ("human", "{input}"),
    MessagesPlaceholder(variable_name="agent_scratchpad")
])

# ── Bind tools to the model ──
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
agent = create_tool_calling_agent(llm, tools, prompt)

# ── AgentExecutor runs the loop ──
executor = AgentExecutor(agent=agent, tools=tools, verbose=True, max_iterations=5)

result = executor.invoke({"input": "What is 2 to the power of 10, and how many words in 'Hello beautiful world'?"})
print(result["output"])
# Agent calls calculator → 1024, then word_count → 3 words, then synthesises answer.

6. Tools langchain_community

Tools are the interfaces through which agents interact with the world. LangChain ships 50+ pre-built tools and makes it trivial to define custom ones. Every tool has a name, a description (used by the LLM to decide when to call it), and a callable function.

python · tools_example.py 
from langchain_core.tools import tool, BaseTool
from pydantic import BaseModel, Field
from typing import Type
import requests

# ── Method 1: @tool decorator (simplest) ──
@tool
def get_weather(city: str) -> str:
    """Get current weather for a city using Open-Meteo (free, no API key)."""
    geo = requests.get(f"https://geocoding-api.open-meteo.com/v1/search?name={city}&count=1").json()
    if not geo.get("results"): return "City not found"
    lat = geo["results"][0]["latitude"]
    lon = geo["results"][0]["longitude"]
    weather = requests.get(
        f"https://api.open-meteo.com/v1/forecast?latitude={lat}&longitude={lon}¤t_weather=true"
    ).json()
    temp = weather["current_weather"]["temperature"]
    return f"Current temperature in {city}: {temp}°C"

# ── Method 2: Class-based Tool (for complex input schemas) ──
class SearchInput(BaseModel):
    query: str = Field(description="The search query string")
    max_results: int = Field(default=3, description="Number of results to return")

class WebSearchTool(BaseTool):
    name: str = "web_search"
    description: str = "Search the web for recent information"
    args_schema: Type[BaseModel] = SearchInput

    def _run(self, query: str, max_results: int = 3) -> str:
        return f"[Mock] Top {max_results} results for '{query}'"

print(get_weather.name)         # get_weather
print(get_weather.description)  # Get current weather...
print(get_weather.invoke({"city": "Hyderabad"}))

7. Document Loaders langchain_community

Document Loaders ingest raw data from any source — PDFs, web pages, CSV files, GitHub repos, Notion pages, YouTube transcripts — and convert them into LangChain's Document objects. Each Document has page_content (the text) and metadata (source, page number, etc.).

python · document_loaders.py 
from langchain_community.document_loaders import (
    PyPDFLoader,        # pip install pypdf
    WebBaseLoader,      # pip install beautifulsoup4
    CSVLoader,
    TextLoader
)
from langchain_text_splitters import RecursiveCharacterTextSplitter

# ── Load a PDF ──
pdf_loader = PyPDFLoader("research_paper.pdf")
pdf_docs = pdf_loader.load()
print(f"Loaded {len(pdf_docs)} pages")
print(pdf_docs[0].metadata)   # {'source': 'research_paper.pdf', 'page': 0}

# ── Load a webpage ──
web_loader = WebBaseLoader("https://python.org/about/")
web_docs = web_loader.load()

# ── Split into chunks for embedding ──
splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,      # ~750 tokens per chunk
    chunk_overlap=200,    # overlap preserves context at boundaries
    length_function=len,
    separators=["\n\n", "\n", " ", ""]
)

chunks = splitter.split_documents(web_docs)
print(f"Split into {len(chunks)} chunks")
print(chunks[0].page_content[:200])

8. Indexes & Vector Stores RAG Pipeline

Vector Stores enable semantic search over your documents. Text is converted into high-dimensional embeddings (numerical vectors), stored in an index, and at query time the closest matching chunks are retrieved and injected into the LLM's context. This is the core of Retrieval-Augmented Generation (RAG).

python · rag_pipeline.py 
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_chroma import Chroma                    # pip install langchain-chroma chromadb
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough
from langchain_community.document_loaders import WebBaseLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter

# ── Step 1: Load & split documents ──
loader = WebBaseLoader("https://docs.python.org/3/library/asyncio.html")
docs = loader.load()
splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=100)
chunks = splitter.split_documents(docs)

# ── Step 2: Embed & store in Chroma ──
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = Chroma.from_documents(chunks, embeddings)
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

# ── Step 3: Build RAG chain ──
rag_prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer using only the provided context.\nContext:\n{context}"),
    ("human", "{question}")
])

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

llm = ChatOpenAI(model="gpt-4o-mini")

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | rag_prompt
    | llm
    | StrOutputParser()
)

answer = rag_chain.invoke("How does asyncio event loop work?")
print(answer)

Architecture & Flow Diagram

The LangChain execution flow begins with a user's natural language input and ends with a structured, grounded, or action-driven output. Below is the canonical flow for an agent-powered application — the most complex and representative path.

Conceptual Flow

👤 User Input natural language
→inject vars
📝 Prompt Template format + context
→API call
🤖 LLM GPT-4 / Claude
→decide
🧠 Agent ReAct loop
→call
🔧 Tools search / APIs
→final
✅ Output parsed response

Full Architecture Diagram

The diagram shows three stacked layers: the Application Layer (user ↔ prompts ↔ output), the LangChain Layer (chains, memory, agents, retriever), and the External Services Layer (LLM providers, databases, tools). LCEL's pipe operator connects everything in the middle tier, while agents loop between the LLM and tools until the task is complete.

docs = [

Real-World Use Cases

01

🏢 Enterprise Knowledge Base Q&A (RAG)

Problem Statement

A company has thousands of internal PDFs — HR policies, technical docs, product manuals — and employees waste hours hunting for answers through search or intranet portals that don't understand natural language.

Solution using LangChain

Ingest all documents with PyPDFLoader, chunk with RecursiveCharacterTextSplitter, embed with OpenAI embeddings, store in Pinecone. Build a RAG chain: employee asks a question → retriever fetches relevant chunks → GPT-4 answers grounded in actual policy text, with source citations. Add RunnableWithMessageHistory for multi-turn follow-ups.

🛒 AI Customer Support Agent with Live Data

Problem Statement

An e-commerce platform needs a 24/7 support bot that can check order status, process returns, answer product questions, and escalate to human agents — all from natural conversation.

Solution using LangChain

Build a tool-calling agent with 4 tools: get_order_status(order_id), initiate_return(order_id, reason), search_products(query), and escalate_to_human(reason). The agent decides which tool to invoke based on the user's message. Memory preserves the conversation state. A ConversationSummaryMemory compresses long histories to stay within token limits.

Advantages & Limitations

✅ Strengths

  • Modular architecture — swap any component (LLM, memory, vector DB) without rewriting logic
  • LCEL gives type-safe, streaming, batch, and async support for free with | composition
  • Massive ecosystem — 100+ integrations for loaders, vector stores, LLM providers, tools
  • Rapid prototyping — a working RAG pipeline in under 30 lines of code
  • LangSmith integration for end-to-end tracing, evaluation, and prompt playground
  • Active community and weekly releases keeping pace with the fast LLM landscape
  • Model-agnostic — same code works with OpenAI, Anthropic, Groq, or a local Ollama model

⚠️ Limitations

  • Steep learning curve — LCEL, Runnables, chains, agents and memory are all separate concepts to master
  • Abstraction overhead — debugging a multi-step chain with callbacks is significantly harder than debugging plain Python
  • Rapid API churn — breaking changes across versions are common; v0.1 → v0.2 → v0.3 migrations required large refactors
  • Latency — multiple LLM hops in agent loops can add seconds of latency per chain step
  • Cost — agentic loops with many tool calls can burn tokens quickly and unpredictably
  • Over-engineering risk — using LangChain for a simple one-shot LLM call adds unnecessary complexity
When NOT to use LangChain: If your application makes a single LLM call with a static prompt, LangChain is overkill — use the OpenAI SDK directly. If you need production-grade determinism, avoid agents (use pre-defined chains). For fine-tuning workflows, use Axolotl or HuggingFace Transformers instead.

Conclusion & Future Scope

LangChain fundamentally changed how developers build with LLMs. By abstracting the messy plumbing of prompt engineering, memory management, tool integration, and multi-step orchestration, it allowed the community to go from prototype to production at unprecedented speed.

⛓️

LCEL's pipe operator is one of the most elegant API designs in modern Python — compose, stream, and batch complex pipelines declaratively.

🧠

Memory is a first-class concern: design your session management strategy early — buffer, window, or summary depending on conversation length.

🎯

Agents are powerful but unpredictable. Always set max_iterations, add guardrails, and trace with LangSmith before deploying.

📚

RAG is the killer feature: grounding LLMs in your private data unlocks enterprise use cases that pure LLMs simply cannot handle.

🔌

Model-agnosticism is real: swapping ChatOpenAI for ChatAnthropic or ChatOllama truly requires one line.

⚠️

Match tool complexity to need: a simple Q&A app needs zero LangChain; an agentic assistant benefits enormously from it.

Future Scope

The LangChain ecosystem is rapidly evolving into something far more powerful than a chaining library:

LangGraph — the next major evolution — treats agent workflows as directed graphs (not linear chains), enabling cycles, branching, and true multi-agent coordination with persistent shared state. Think state machines powered by LLMs.

Multi-Agent Systems — the frontier is hierarchical agent networks where a supervisor agent delegates tasks to specialised sub-agents (a coder agent, a search agent, a QA agent) in a collaborative loop.

LangSmith & Evals — as LLM applications mature, systematic evaluation and observability become critical. LangSmith's dataset-driven testing and production tracing are becoming essential for any serious deployment.

The bottom line: LangChain is the foundational layer of the modern AI application stack. Mastering it — its primitives, its patterns, and its limitations — is one of the highest-leverage skills a developer can develop in the current AI era.

Key Insight: LangChain isn't magic — it's disciplined engineering. The developers who get the most out of it are those who understand the primitives deeply enough to know when not to use an abstraction, and when to drop down to raw Runnable composition for full control.
